# Лабораторная работа №4 — полный разбор и защита

**Вариант 13 — «Учёт продуктов в магазине. Категории изделий».**
Тема: разработка микросервиса.

---

## 1. Что требовалось

1. Реализовать простой микросервис — Web API для CRUD одной сущности.
2. Настроить контейнер для запуска микросервиса.
3. Проверить работу через Swagger/Postman.

Для варианта 13 сущность — **категория изделия** из простого справочника
лабораторной №2. У неё одно текстовое поле — название.

Обязательные endpoint:

* `GET` — список;
* `POST` — добавление;
* `PUT/<string>` — изменение;
* `DELETE/<string>` — удаление.

По заданию логика должна находиться **прямо в контроллере**, без сложной
многослойной архитектуры.

## 6. API

Базовый маршрут: `/api/categories`.

| Метод | Маршрут | Результат |
|---|---|---|
| `GET` | `/api/categories` | список всех категорий |
| `GET` | `/api/categories/{name}` | категория по названию |
| `POST` | `/api/categories` | `201 Created` |
| `PUT` | `/api/categories/{name}` | `204 No Content` |
| `DELETE` | `/api/categories/{name}` | `204 No Content` |

Тело `POST`/`PUT`:

```json
{
  "name": "Кондитерские изделия"
}
```

`PUT`: в URL — старое название, в теле — новое.

Коды ошибок:

* пустое название — `400 Bad Request`;
* категория не найдена — `404 Not Found`;
* дубликат при создании/переименовании — `409 Conflict`.

## 7. Хранение в ветке lab4 — SQLite

* Пакет `Microsoft.Data.Sqlite`;
* файл `categories.db` рядом с исполняемым файлом;
* таблица:

```sql
CREATE TABLE Categories (
    Id INTEGER PRIMARY KEY AUTOINCREMENT,
    Name TEXT NOT NULL UNIQUE
);
```

* при первом запуске добавляются 4 категории;
* Dockerfile задаёт `CATEGORIES_DB_PATH=/data/categories.db` и создаёт `/data`;
* база сохраняется в Docker volume.

## 8. Хранение в ветке lab5 — PostgreSQL

* Пакет `Npgsql`;
* connection string `ConnectionStrings:Postgres`;
* таблица:

```sql
CREATE TABLE Categories (
    Id SERIAL PRIMARY KEY,
    Name TEXT NOT NULL UNIQUE
);
```

* PostgreSQL запускается отдельным контейнером `postgres:16`;
* при старте контроллер ждёт доступности БД и создаёт/заполняет таблицу;
* в Docker Compose строка подключения задаётся переменной
  `ConnectionStrings__Postgres`.

## 9. Docker

Dockerfile — многоступенчатый:

1. `sdk:9.0` — restore, publish;
2. `aspnet:9.0` — только опубликованные файлы;
3. `ASPNETCORE_URLS=http://+:8080`;
4. `EXPOSE 8080`.

Сборка и запуск в ветке lab4:

```powershell
docker build -t product-categories-api lab4/src/ProductCatalog.CategoriesApi
docker run -d -p 8080:8080 -v categories-data:/data product-categories-api
```

В ветке lab5 сервис запускается через `lab5/docker-compose.yml` вместе с
PostgreSQL и products-api.

Swagger: `http://localhost:8080/swagger`.

## 11. Вероятные вопросы и ответы

**Почему нет репозитория/сервисного слоя?**
По заданию логика должна быть в контроллере; для простого CRUD дополнительные
слои не нужны. Это осознанное упрощение.

**Почему в lab4 SQLite, а в lab5 PostgreSQL?**
Для lab4 достаточно файловой БД и одного контейнера. В lab5 требуется БД в
контейнере и общая БД для двух сервисов, поэтому PostgreSQL.

**Как проверяется дубликат?**
Перед `INSERT`/`UPDATE` выполняется `SELECT COUNT(*)`; при дубликате —
`409 Conflict`. В БД также есть `UNIQUE`.

**Что делает `PUT`, если категории нет?**
Возвращает `404 Not Found`; если новое имя уже занято — `409 Conflict`.

**Почему `GET` по имени, а не по Id?**
Для справочника название — естественный ключ, а в задании `PUT`/`DELETE`
используют строковый параметр.

**Как работает Dockerfile?**
Первый stage собирает и публикует приложение, второй — только runtime-образ
ASP.NET без SDK. Это уменьшает размер образа.

**Где хранится БД в контейнере?**
В lab4 — в `/data` (volume), в lab5 — в отдельном контейнере PostgreSQL
(volume `postgres-data`).

**Почему Swagger включён в Production?**
Для учебного стенда удобно проверять API в контейнере; в реальном проекте
Swagger обычно ограничивают окружением Development.
